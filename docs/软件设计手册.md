## 1. 系统概述

### 1.1 产品定位

快速标注模型与训练平台是一个**双引擎文档标注与 NER 模型训练平台**，面向需要对 PDF/图片格式的标准化文档进行信息提取、标注和模型训练的领域用户（如质检标准、合规文档、技术规范等）。

系统提供两种标注引擎：

| 引擎 | 原理 | 特点 |
|------|------|------|
| **规则引擎** | 正则匹配 + 关键词上下文 | 零训练成本，即开即用，覆盖常见标注需求 |
| **模型引擎** | BERT+CRF 序列标注 | 可训练定制，支持持续学习，精度更高 |

### 1.2 核心功能

```
┌─────────────────────────────────────────────────────┐
│               快速标注模型与训练平台                    │
├───────────────┬──────────────┬──────────────────────┤
│  文档解析      │  快速标注     │  模型训练与管理        │
├───────────────┼──────────────┼──────────────────────┤
│ · PDF/图片上传 │ · 规则标注    │ · 上传JSONL训练数据    │
│ · 多后端解析   │ · 模型标注    │ · BERT+CRF训练        │
│ · 高精度OCR   │ · 双引擎融合  │ · 实时Loss曲线        │
│ · 版面分析     │ · 导航浏览    │ · 模型评估(F1)        │
│ · Markdown输出 │ · 置信度过滤  │ · 模型下载/删除        │
└───────────────┴──────────────┴──────────────────────┘
```

### 1.3 技术栈

| 层次 | 技术选型 | 说明 |
|------|----------|------|
| 前端框架 | Vue 3 (Composition API) | 单文件应用 (App.vue) |
| 构建工具 | Vite 5 | 开发服务器端口 3000 |
| UI 渲染 | chart.js + marked | 训练曲线可视化 + Markdown 渲染 |
| 后端框架 | FastAPI + uvicorn | 异步 HTTP 服务，端口 8267 |
| 深度学习 | PyTorch 2.x + Transformers | BERT NER 模型训练/推理 |
| 预训练模型 | chinese-roberta-wwm-ext | 中文序列标注 backbone |
| 序列标注 | Linear + CRF | BIO 编码，Viterbi 解码 |
| 文档解析 | MinerU (CLI) | Pipeline/VLM 双后端 |
| 网络架构 | Vite Proxy | 前端 3000 → 代理 → 后端 8267 |

### 2.2 网络架构

遵循「前端 API 相对路径 + Vite Proxy 代转」模式：

```
前端 (Vite Dev Server, 0.0.0.0:3000)
  ├── /@, /src, /node_modules, /assets → Vite 自身处理
  └── 其他所有请求 → Proxy → http://127.0.0.1:8267 (后端)

后端 (uvicorn, 0.0.0.0:8267)
  └── 不直接对外暴露，所有外部请求通过 Vite Proxy 代转
```

### 2.3 核心设计原则

1. **双引擎互补**: 规则引擎提供零成本的 baseline；模型引擎提供可训练的 precision。两者输出可融合，通过置信度阈值控制。
2. **异步非阻塞**: 文档解析（子进程）和模型训练（独立线程）均通过异步机制隔离，不阻塞 HTTP 事件循环。
3. **渐进式进度**: 训练和解析均通过 SSE（Server-Sent Events）实时推送进度到前端。
4. **无数据库设计**: 使用文件系统存储模型、任务记录和输出结果，简化部署。
5. **单文件前端**: 整个前端 UI 合并为一个 `App.vue`（~7000 行），避免路由和组件拆分带来的上下文分散。

## 3. 子系统设计

### 3.1 文档解析子系统

#### 3.1.1 功能概述

接收用户上传的 PDF/PNG/JPG 文档，调用 MinerU 命令行工具进行版面分析、OCR 识别和 Markdown 转换，输出 layout PDF 和 Markdown 文件。

#### 3.1.2 模块划分

```
backend/main.py
  ├── /upload                 → 接收文件 + 配置
  ├── /progress/{task_id}     → 轮询进度
  ├── /result/{task_id}/pdf   → 获取 layout PDF
  ├── /result/{task_id}/md    → 获取 Markdown
  ├── /result/{task_id}/images/{path} → 获取图片
  └── /options                → 获取可选配置项

backend/mineru_runner.py      → MinerU CLI 包装器
  ├── apply_quality_overrides → 高精度参数注入
  ├── _patch_pdf_render_dpi  → PDF 渲染 DPI 覆写 (高精度=560)
  ├── _patch_ocr_runtime     → OCR 检测阈值覆写
  ├── _patch_small_text_runtime → 小文本增强
  └── main()                 → 调用 mineru.cli.do_parse
```

#### 3.1.3 解析流程

```
用户上传文件
    │
    ▼
生成 task_id (UUID4) 并保存文件到 input/{task_id}/
    │
    ▼
创建后台异步任务 process_file(task_id)
    │
    ▼
构建 MinerU 命令行参数
  · backend: pipeline | vlm-auto-engine | hybrid-auto-engine
  · language: ch | en | auto
  · parse_method: auto | ocr | txt
  · 功能开关: formula, table
    │
    ▼
启动 MinerU 子进程 + 流式读取 stdout/stderr
    │
    ▼ (并行)
进度推进循环（每 2 秒更新一次）
  · 使用指数平滑曲线计算进度百分比
  · 根据已用时间/预估总时间动态调整
    │
    ▼
进程结束后扫描 output/{task_id}/ 目录
  · 查找 *_layout.pdf → layout PDF
  · 查找 *.md → Markdown 结果
  · 查找 images/ → 图片目录
    │
    ▼
结果存入 progress_store[task_id]
```

#### 3.1.4 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| backend_type | pipeline | 后端引擎：pipeline / vlm |
| language | auto | 语言：auto / zh / en / zh_en |
| ocr_mode | auto | OCR模式：auto / force_ocr / text_first |
| high_accuracy | true | 高精度模式（提升 DPI 到 560） |
| enable_ocr | true | 启用 OCR 识别 |
| enable_layout | true | 启用版面分析 |
| enable_formula | false | 启用公式识别 |
| enable_table | true | 启用表格识别 |
| enable_image | true | 提取图片区域 |
| enable_heading | true | 标题分级恢复 |
| preserve_whitespace | true | 保留空白细节 |

#### 3.1.5 高精度模式 (Quality Overrides)

当 `high_accuracy=true` 时，mineru_runner.py 会对 MinerU 的底层运行时参数进行 Monkey Patch：

| 参数 | 普通模式 | 高精度模式 |
|------|----------|------------|
| PDF 渲染 DPI | 220 | 560 |
| OCR 检测框阈值 | 0.28 | 0.18 |
| OCR 检测框扩展比 | 1.9 | 2.3 |
| 检测边长限制 | 1088 | 1536 |
| 结果丢弃分数 | 0.45 | 0.28 |
| 最小置信度 | 0.5 | 0.36 |

此外，还对小文本区域进行 CLAHE 增强和自适应缩放，提升细小文字的 OCR 识别率。

### 3.2 规则标注子系统

#### 3.2.1 功能概述

基于预定义的正则规则对解析后的 Markdown 文本进行实体提取，返回命中实体和上下文片段。支持 5 种标注规则。

#### 3.2.2 标注规则

| 规则 ID | 规则名 | 匹配逻辑 | 示例 |
|---------|--------|----------|------|
| standards | 标准条文 | 正则匹配标准编号 (GB、ISO、IEC等) | GB/T 26572-2025 |
| decisions | 判定结论 | 关键词 + 排除规则匹配 | "不符合表3要求" |
| dates | 日期节点 | 正则 + 日期合法性 + 上下文关键词 | 2025-06-01 |
| limits | 限值指标 | 数值+单位正则 (ppm, mg/kg等) + 对比式 | ≤100 mg/kg |
| numeric_facts | 数值信息 | CAS号、网格尺寸、比例等复合正则 | 100×50×20mm |

#### 3.2.3 标注流程

```
加载 Markdown 文本
    │
    ▼
文本归一化 (去除 HTML、Markdown 转义等)
    │
    ▼
分句处理 (按换行、句号、分号等分割)
    │
    ▼
┌─ standards: STANDARD_CODE_PATTERN.finditer()
├─ decisions: 分句匹配 decision 关键词 + 排除模式
├─ dates: DATE_PATTERN.finditer() + 日期合法性验证
├─ limits: 数值+单位 / 对比式 正则 + 限值上下文
└─ numeric_facts: CAS/网格/比例 + 数值上下文
    │
    ▼
去重合并 (按 rule_id + text + type)
    │
    ▼
输出: { rules[], entities[], snippets[], counts{} }
```

#### 3.2.4 数据增强

标注引擎内置以下文本处理策略：

- **Markdown 转义字符清洗**: 去除 `\*`, `\_` 等用于 Markdown 的转义，确保实体文本匹配不受影响
- **HTML 解码**: 处理 `&amp;`, `&#xa0;` 等 HTML 实体
- **去结构噪声**: 过滤纯标题、纯编号、纯数字行等误匹配
- **上下文窗口提取**: 每个实体附带前后 180 字符上下文
- **分句过滤**: 最短句子 ≥ 8 个字符

### 3.3 模型训练子系统

#### 3.3.1 模型架构

```
输入文本
    │
    ▼
chinese-roberta-wwm-ext (Transformer Encoder)
    │ hidden_states (B, S, 768)
    ▼
nn.Linear(768, num_labels)
    │ emissions (B, S, num_labels)
    ▼
CRF (Linear-Chain Conditional Random Field)
    │ 输出: NLL Loss (训练) / Viterbi 路径 (推理)
    ▼
BIO 标签序列
```

#### 3.3.2 训练数据格式

支持 Doccano JSONL 格式及两种兼容格式：

```json
// 格式1: Doccano entities (推荐)
{"text": "GB 26572-2025 规定了玩具安全要求", "entities": [
    {"start_offset": 0, "end_offset": 13, "label": "标准编号"},
    {"start_offset": 16, "end_offset": 26, "label": "法规对象"}
]}

// 格式2: spans (Doccano 导出)
{"text": "...", "spans": [{"start": 0, "end": 13, "label": "标准编号"}]}

// 格式3: labels 列表
{"text": "...", "labels": [[0, 13, "标准编号"], [16, 26, "法规对象"]]}
```

#### 3.3.3 BIO 编码方案

```
标签集映射:
  O           → 0  (非实体)
  B-标准编号  → 1  (标准编号 开始)
  I-标准编号  → 2  (标准编号 内部)
  B-法规对象  → 3  (法规对象 开始)
  I-法规对象  → 4  (法规对象 内部)
  ...
```

编码时对齐 tokenizer 的 offset_mapping，每个 token 分配一个 BIO 标签。特殊 token ([CLS], [SEP], [PAD]) 标记为 -100（loss 忽略）。

#### 3.3.4 训练参数与策略

| 策略 | 说明 |
|------|------|
| **自适应超参数** | 根据样本数量自动调整 epochs/batch_size/lr |
| **Warmup + Cosine 衰减** | 前 10% 步线性 warmup，后续 cosine 衰减至 0 |
| **FGM 对抗训练** | 对 embedding 层加梯度方向扰动，增强鲁棒性 |
| **梯度裁剪** | max_norm=1.0 |
| **EMA Loss** | 指数移动平均平滑 Loss 曲线 |
| **早停 (Early Stopping)** | 验证集 loss 不再下降后 patience=2 轮自动停止 |
| **验证集划分** | 样本 ≥ 20 时自动划分 10% 验证集 |
| **动态 max_length** | 根据平均文本长度自动选择 192/256/384/512 |

训练循环采用**纯 PyTorch 手动循环**而非 HuggingFace Trainer，避免兼容性问题并提供对训练细节的完全控制。

#### 3.3.5 数据增强

`_augment_training_data()` 执行：

1. **上下文扩展**: 若用户只标注了孤立实体文本（如只有 "GB/T 26572—2011"），自动从原始文档中找到包含该实体的完整句子，用完整句子替换
2. **负样本注入**: 从未标注的句子中随机采样作为负样本（entities=[]），数量与正样本相当（最多 3 条），教会模型预测 O 标签

#### 3.3.6 继续训练

支持在已有模型基础上用新数据继续训练（增量学习）：
- 合并旧样本与新样本
- 重新收集 BIO 标签（支持新增实体类型）
- 使用较小的学习率继续训练
- 覆盖保存模型文件

### 3.4 模型推理与标注子系统

#### 3.4.1 推理流程

```
输入: Markdown 文本 + model_id
    │
    ▼
加载模型 (优先内存缓存，否则从磁盘)
    │
    ▼
分句处理 (按相同分句规则)
    │
    ▼
逐句推理:
  · tokenize → offset_mapping
  · model forward → CRF Viterbi 解码
  · BIO 标签 → 实体列表 (字符偏移)
    │
    ▼
置信度计算: 实体包含的所有 token 的 softmax 概率均值
    │
    ▼
边界修复: "OP05" 前缀合并 (常见于标准编号)
    │
    ▼
输出: { entities[], entries[], counts[], rules[] }
```

#### 3.4.2 双引擎融合

前端标注工作台同时支持规则标注和模型标注：

```
                   Markdown 文本
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
    规则引擎标注                  模型引擎标注
    (后端 /annotations)          (后端 /model/infer)
          │                           │
          ▼                           ▼
    规则实体 + 片段              模型实体 + 片段
          │                           │
          └─────────────┬─────────────┘
                        ▼
              前端 mergeAnnotationResults()
                        │
          ┌─────────────┴─────────────┐
          │                           │
          ▼                           ▼
    规则实体 (全收)            模型实体 (置信度过滤)
          │                           │
          └─────────────┬─────────────┘
                        ▼
              统一高亮渲染 (highlightHtmlContent)
              按 DOM 遍历顺序构建命中片段列表
                        │
                        ▼
              用户通过导航浏览标注结果
```

融合结果通过 DOM 遍历统一排序，确保高亮与命中片段 1:1 精确对应。

#### 3.4.3 置信度过滤

用户可通过滑块调整模型标注的置信度阈值（0-100%），低于阈值的实体不显示。预设值: 25%、50%、70%、90%。

#### 3.5.3 模型评估

评估功能计算标准的 NER 评估指标：

```
评估指标:
  · 严格匹配 (Exact Match): start_offset + end_offset + label 全部一致
  · Precision = TP / (TP + FP)
  · Recall    = TP / (TP + FN)
  · F1        = 2 * P * R / (P + R)
  · 每类指标 (Per-class): 每个实体类型独立计算
  · 宏平均 (Macro Average): 各类指标的算术平均
```

评估流程: 加载测试 JSONL → 逐条推理 → 收集 y_true/y_pred → 计算指标。

---

### 3.6 历史管理子系统

#### 3.6.1 任务生命周期

```
创建: /upload → task_id 生成，文件存入 input/{task_id}/
处理中: status=processing → MinerU 进程运行
完成: status=completed → output/{task_id}/ 包含结果
失败: status=failed → 记录错误信息
删除: /history/{task_id} DELETE → 清理 input/ output/ progress_store
```

#### 3.6.2 状态恢复

服务重启后，历史记录通过扫描 `input/` 和 `output/` 目录自动恢复。正在进行中的任务状态会丢失（progress_store 为内存存储）。

| POST | `/model/evaluate` | 评估模型性能 | JSON |

### 5.2 SSE 流式接口

训练接口（`/model/train`, `/model/upload-and-train`）使用 Server-Sent Events：

```
event stream:
  data: {"type": "status", "message": "加载模型..."}
  data: {"type": "progress", "epoch": 0.5, "step": 25, "loss": 0.8234, ...}
  data: {"type": "validation", "val_loss": 0.52, "val_accuracy": 0.87}
  data: {"type": "log", "message": "epoch 1/5 done"}
  : heartbeat\n\n
  data: {"type": "complete", "result": {...}}
```

心跳间隔 0.3s，确保连接保持活跃。

## 8. 关键设计决策

### 8.1 为何不使用数据库

**决策**: 使用文件系统代替数据库存储

**理由**:
- 数据以文件为主（PDF、Markdown、模型文件），天然适合文件系统存储
- 元信息量小（每个任务几十个字段），JSON 文件足够
- 零配置，即开即用，降低部署复杂度
- 任务状态通过内存字典管理，无需持久化中间状态

**代价**: 服务重启后进行中的任务状态丢失；多实例部署受限于共享文件系统。

### 8.2 为何使用纯 PyTorch 训练循环而非 HuggingFace Trainer

**决策**: 自定义训练循环

**理由**:
- CRF 层非标准 HuggingFace 模型组件，Trainer 不易集成
- 需要 FGM 对抗训练的细粒度控制
- EMA Loss 平滑需要自定义逻辑
- 避免 Trainer 的抽象开销和兼容性问题

### 8.3 为何使用单文件前端 (App.vue)

**决策**: 7000+ 行单文件 Vue 组件

**理由**:
- 项目处于快速迭代阶段，页面间共享大量状态
- 避免组件拆分带来的 props/emits 传递复杂度
- 减少文件切换和上下文分散

**代价**: 单文件较大，新开发者阅读成本高；后续维护应考虑适度拆分。

### 8.4 为何使用 Vite Proxy 而非直接暴露后端

**决策**: 前端 API 使用相对路径，通过 Vite Proxy 代转到后端

**理由**:
- 局域网其他设备只需访问前端端口（3000），无需直连后端
- 避免跨域问题和防火墙配置
- 后端不直接对公网暴露，安全性更高

### 8.5 双引擎融合策略

**决策**: 规则和模型结果在前端合并，而非后端

**理由**:
- 规则标注和模型标注是独立的 POST 请求，用户可以单独调用
- 前端可以根据 UI 交互动态调整融合策略（如置信度阈值滑块）
- 避免后端耦合两个标注逻辑

### 8.6 训练数据增强

**决策**: 自动进行上下文扩展和负样本注入

**理由**:
- 用户标注的实体往往是孤立的（从文档中摘抄的片段），缺乏上下文
- BERT 等预训练模型需要完整句子级别的上下文才能有效编码
- 负样本教会模型识别"不是实体"的部分，防止模型只输出实体标签
